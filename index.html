Architecture & Request Flow

A cluster is one or more control-plane nodes plus a pool of worker nodes, connected by a virtual network so the whole thing behaves like one large machine with pooled resources.

Why Kubernetes exists

Apps today are built as microservices — code and dependencies packaged into isolated containers. Containers are great in isolation, but manual container management breaks down three ways once you have more than a handful:

  1. The host runs out of resources and containers can't scale further.
  2. Containers die and nothing notices or restarts them.
  3. The host machine itself dies, and every container on it dies with it, with nothing to bring them back.

Kubernetes automates container lifecycle, scaling, and recovery across many machines at once — guaranteeing high availability (no downtime), scalability (fast scale up/down under load), and a path to disaster recovery (backup/restore, mostly via etcd snapshots).

Control plane vs. worker nodes

Worker nodes run your actual application Pods — the real workload. Control-plane nodes run the cluster's "brain" and, in most setups, are deliberately kept free of regular workload Pods so their resources stay available for managing the cluster itself. Production clusters should run at least two control-plane nodes — losing your only one means losing cluster access entirely.

    YAML Anatomy

    All cluster configuration is sent to the API server as YAML (or JSON) — this is the language you use to talk to Kubernetes.

    The declarative model

    You declare the desired state; Kubernetes continuously works to make actual state match it. That reconciliation loop is the basis of self-healing — if a replica dies, the Controller Manager notices and recreates it. Critically, kubectl apply itself is a one-time action: it reads your file, patches the difference into the cluster, and exits. Whether anything keeps enforcing that state afterward depends entirely on what kind of object you created — a bare Pod has nothing watching it; a Deployment's ReplicaSet does.

    Two YAML data types you'll use constantly

    Lists / sequences — items prefixed with a dash:

    - milk
- eggs
- bread

    Dictionaries / mappings — key/value pairs, order doesn't matter:

    flavor: chocolate
expires: June 30
organic: true

    Indentation = ownership. Anything indented under a key belongs to that key. Nesting lists inside dictionaries (and vice versa) is how complex manifests are built. Tip: never write a manifest from scratch — search the Kubernetes docs for the object type and adapt the example. It saves you from indentation and typo disasters.

    Every manifest has the same three parts

    apiVersion: v1     # which API handles this object type — must match, or you get errors
kind: Pod          # case-sensitive! "pod" is not the same as "Pod"
metadata:
  name: nginx      # 1. Metadata — name, labels, etc.
spec:              # 2. Specification — the config specific to this object type
  containers:
    - name: nginx
      image: nginx  # must be spelled correctly or the image won't be found
# 3. Status — auto-generated & continuously updated by Kubernetes, sourced from etcd.
#    You never write this yourself; kubectl get/describe shows it to you.

    Gotchas worth memorizing

    • apiVersion changes across Kubernetes versions — upgrading a cluster can deprecate old API versions and silently break old manifests.
    • kind is case-sensitive: Pod ≠ pod.
    • Keys are camelCase: configMap, not Configmap or config_map.
    • spec.containers (and most nested resource lists) is a YAML list — don't forget the leading dash.
    • A Deployment's spec.selector.matchLabels must exactly match spec.template.metadata.labels — this is the single most common cause of "my pods aren't showing up."
